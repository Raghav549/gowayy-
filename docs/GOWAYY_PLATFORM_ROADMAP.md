# Gowayy — Three-App Production Architecture & Delivery Plan

Date: 2026-11-28. Source audited: Raghav549/gowayy- (main, bfbe38ff). Existing Vercel customer deployment: gowayydlng (production, READY); database health endpoint confirms Neon is reachable. This is a staged implementation plan, **not** a claim that the platform is already live end-to-end.

## Existing-code findings (must fix before merchant launch)
- Customer checkout uses **gowayy-sandbox**, which simulates UPI/card success; actual money never moves.
- Customer signup grants a simulated ₹500 wallet bonus; brand-new seed data includes predictable admin and demo credentials. Audit and rotate/remove those privileged accounts before enabling privileged production workflows.
- Order progression is fake, generated by a timer (12/35/80/150 seconds), and riders/phones are random; cab drivers, vehicles, OTPs, and ETAs are also synthetic.
- Admin is embedded under /admin within customer app and exposes only limited catalogue/order changes; homepage category rail and banners live as hard-coded constants.
- Listings are seeded, not verified merchant inventory; image URLs and hero media are local assets.
- Hotel bookings do not reserve room-night inventory atomically; cab bookings do not lock a vehicle/driver/slot. Payment, cancellation, settlements, availability, and observability require real services.

## Deployment and source protection
- Preserve main and production customer deployment; develop on feature branches and review through PRs and preview builds.
- Keep three Next.js frontends with a single shared backend/API and Postgres, not three independent databases:
  - Gowayy Customer — existing repo and production URL.
  - Gowayy Business — independently deployable Next.js frontend, same logo/visual tokens.
  - Gowayy Admin — independently deployable Next.js frontend, same logo/visual tokens.
  - Shared API — first extract from existing authenticated route handlers; later deploy a standalone service if cross-domain sessions and webhooks require it.
- Prefer monorepo with apps/customer, apps/business, apps/admin, packages/ui, packages/db, packages/contracts, packages/auth; migrate the existing customer without changing user-facing routes. Independent repositories are optional only if the shared contracts are versioned and CI-enforced.
- All state-changing operations go through the shared API. Use the current Neon database, with a separate staging branch/database for migrations and tests, backups, and expand/contract schema rollout. Never copy live secrets to repositories.

## Principal roles and authorization
- Platform superadmin, operational admin, finance support, content editor, shop/restaurant/grocery owner, hotel owner, cab fleet owner, manager/staff/driver, customer.
- User identity is global, business membership per organization. Tables: organizations, memberships (user_id, organization_id, role, status), vendor_ownership, hotel_ownership, fleet_ownership, approval_requests, audit_logs, invitations.
- Enforce organization and object ownership on the **server for every query**; UI-only hiding is insufficient. Sensitive operations require re-auth/2FA, append-only audit records, and dual approval on high-risk payment/refund actions.
- Customer signup/login must never grant merchant/admin privileges. Business self-signup -> verification pending -> entity details -> KYC/document review -> admin approval -> dashboard. Invitation-based staff accounts get scoped permissions.
- Eliminate seed passwords and test-wallet grants for real users. Implement CSRF defense, secure cookie attributes, strong session rotation/revocation, login throttling, and validation.

## Gowayy Admin — operational control
- Dashboard: real order/booking/payment KPIs (only settled amounts counted as revenue), refund exceptions, live partner onboarding and SLA alerts.
- CMS: add/edit/archive/remove and reorder home categories, category images, gradient theme, banners, headline/copy/target/expiry, homepage sections, landing cards; optimized media upload with preview, alt text, duplicate checks and media library.
- Entire catalogue: shops, restaurants, grocery vendors, products, prices, stock, category taxonomy, food menus, hotel listings/photos/rooms/rates/calendar, tours/itineraries, cab types/vehicles/routes/driver eligibility and promotion slots. Approval, revision history, rollback, soft deletion for booked/ordered entities.
- Orders: status corrections with reasons, human assignment, exception resolution, returns/refunds, disputes and immutable event history.
- Partners: applications, identity/permission review, suspend/reactivate, verification, payouts; customers, support tickets, announcements and moderation.
- Payments: provider webhook logs, ledger reconciliation, settlement queues, manual review; never accept browser-supplied 'paid' or 'refunded' flags.
- Security/ops: audit log, rate-limits, feature flags, health/errors, metrics, data exports, backup/restore drills, break-glass workflow.

## Gowayy Business — signup and contextual dashboards
1. Signup/login -> email/phone verification -> choose merchant type (shop / grocery / restaurant / hotel / cab fleet / tour operator) -> business identity, address/location, contact, documents, tax details if applicable, settlement account -> pending approval -> admin review -> approved business dashboard.
2. **Shop / Grocery:** business hours, delivery radii, categories, products, variants, pricing, stock and low-stock alerts, photos, multiple outlets, prep/fulfilment, packing, pickup, returns, accounting.
3. **Restaurant:** menus, categories, modifiers, dietary/allergen fields, open/closed/busy, prep ETA, kitchen queue, order accept/reject, service radius, real fulfilment.
4. **Hotel:** property details, room types, room units, date-specific rates and blackout calendar, availability, policies, add-ons, check-in/out, staff roles, confirmed/rescheduled/cancelled bookings. Lock room nights transactionally against overlap.
5. **Cab fleet:** company and driver onboarding, documents/expiry, vehicle classes and seating, driver schedules, trip pickup/drop, route and fare estimates, dispatch, accept/reassign, live GPS sharing only with consent, trip OTP, start/end and disputes. No fake vehicle/driver allocation.
6. **Tour operator:** packages, departures, occupancy, itinerary, local partners, inventory-linked room/cab bundles and cancellations.
7. Shared owner tools: team roles, earnings reports, payouts, support, notifications, media uploads, opening hours, activity audit and real customer feedback.

## Shared backend contract
- Domain tables: users, sessions, organizations, memberships, destinations, homepage_categories, home_banners, vendors, products, inventory_movements, hotels, room_types, room_units, room_nights, fleets, vehicles, drivers, availability_slots, tours, packages, orders, order_items, order_events, bookings, payment_intents, payments, refunds, ledger_entries, notifications, delivery_assignments, location_updates, audit_logs, outbox_events.
- Database uniqueness, foreign keys, scoped indexes and constraints. Transactions for placing orders, decrementing stock and reserving inventory; enforce idempotency keys on checkout and payment-webhook receipts.
- Server state machines: placed -> accepted -> preparing -> ready -> assigned -> picked_up -> delivered, plus cancelled/failed/refunded; booking: requested/held -> payment_pending -> confirmed -> in_service -> completed/cancelled/refunded.
- Changes trigger transactional outbox, background delivery and cache invalidation; customers, merchants and admin see the same canonical ID and state. Poll/SSE/realtime gateway with versioned events and reconnect recovery.
- Payments: integrate a compliant Indian provider with server-created orders/payment intents and cryptographically verified webhook or provider API reconciliation; never mark paid based on frontend callbacks. Keep COD as pending until collection. UPI deep links alone **cannot** reliably verify receipt. Refund to original method through PSP, not an internal wallet substitute. Production checkout stays disabled for digital money until onboarding and test-settlement evidence are complete.
- Location: real delivery partner GPS with consent, expiration and privacy controls. No synthetic phone numbers, travel promises or live-tracking flags.

## Homepage imagery and speed
- Replace category images and banners with original properly licensed 2.5D style artwork mapped to actual category semantics. No placeholder or deceptive offer text. Maintain the existing lavender/violet glassmorphism visual language and identical Gowayy wordmark.
- Generate responsive AVIF/WebP derivatives (e.g. 120/240px categories; 480/960/1456px banners), precompress, set dimension/aspect ratio, blur/data-colour placeholder, CDN caching and immutable fingerprinted URLs. Never serve image data as DB blobs.
- Preload only above-the-fold hero and first visible category assets; lazy-load below the fold. Use srcSet/sizes and avoid duplicate full-resolution fetches. Audit remote photos and cache lifetimes.
- 'Instant loading on any network' is physically impossible; target immediate skeleton/placeholder and fast visual completion with performance budgets (e.g. p75 LCP <=2.5s on measured mobile profile; CLS <=0.1) and test under throttled 3G/offline.
- CMS changes invalidate cache tags and use versioned image URLs so users see updates without stale artefacts.

## Delivery stages, acceptance gates
**0. Backup, baseline, diagnosis:** snapshot DB, inspect admin access and payment ledger, document existing UX/routes and perf; unchanged customer production and rollback works.
**1. Harden platform:** remove unsafe defaults, rotate exposed privileged accounts, turn off fake progress/paid statuses for real flows, add migration scripts and server-side role tests; unauthorized tenant access rejected (403) and existing customer regression passes.
**2. CMS + image optimization:** admin can create/edit/archive/reorder categories/banners and all listing media; customer reflects edits after cache invalidation, old images don't break and p75 perf budgets met.
**3. Business app:** authenticated, approved merchant only; shop/restaurant product stock and order acceptance reflected in existing customer app; denied merchant cannot mutate another merchant.
**4. Hotel/cab/tour inventory:** valid booking reserves actual room nights or dispatch capacity; simultaneous collision test cannot overbook; cancellations release resources exactly once.
**5. Payment and delivery:** provider test webhook signature, replay attack, timeout, cancellation and reconciliation tests; COD pending until collection; real rider assignment/GPS tested with consent; no auto fake progress.
**6. Production release:** automated typecheck/lint/build, unit/integration/e2e, mobile/responsiveness, accessibility, load, security and payment settlement checks; deploy Business/Admin to their own Vercel projects; monitor and roll back safely.

## Payment troubleshooting runbook
- Reproduce with a test account on isolated staging; collect HTTP method/status/request ID and logs, not secrets.
- Confirm customer submit -> authenticated API -> stock/price revalidation -> order intent -> provider init -> external payment -> signed webhook -> database payment state -> customer confirmation.
- Check for sandbox adapter still selected, wallet test credit, CSP/redirect issues, invalid origin, unauthorized session, missing env key names, callback/webhook domain mismatch, duplicate idempotency keys, missing DB constraints, and incomplete compensating refund.
- Compare Vercel function region (iad1 in observed health) to Neon region and measure request latency.
- Never claim a transaction succeeded without server-side provider verification.

## Non-goals until real integrations exist
No claim of actual merchants, available hotel rooms, assigned driver, live GPS, paid UPI or guaranteed delivery until each integration has independent operational proof.
